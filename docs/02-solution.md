# 设计、动态决策与技术取舍

## 调用流程

CLI 读取 JSON → 校验问题与历史 → 从历史解析缺失主题 → 模型决定一个动作 → 工具执行 → 观察回传模型 → 模型继续查证或结束 → 应用验证证据与冲突 → 生成原文式结果。

`Agent.run` 只规定循环骨架、可用动作和安全边界；live 模式下一次执行哪个工具、检索词、读取顺序、失败后重试或停止、何时结束均来自模型返回 JSON。系统提示要求模型输出简要公开决策依据，不要求内部推理。动作字段由 `validate_action` 严格校验，未知工具和额外字段不执行。

| 模块 | 职责 |
|---|---|
| OpenAICompatibleModel | 每轮发送系统提示、问题、历史、已执行动作和观察，解析下一个 JSON 动作 |
| OfflineMock | 基于观察返回预定义策略，用作确定性测试替身 |
| KnowledgeTools.search | 按主题词和同义词检索，未知主题用关键词回退；完整返回有限库命中项 |
| KnowledgeTools.read | 按 ID 返回原文及版本、范围、规范值 |
| Agent | 步数预算、动作校验、工具异常封装、证据完整性、冲突约束、引用与 Trace |

## 决策与保障边界

模型可选 `search(query)`、`read(document_id)`、`finish(status)`。读取必须先有检索结果。检索后发现多个同主题文档应逐一读取；模型漏读冲突来源时，finish 会收到 unread_evidence，模型可据此继续读取。即使模型要求 answered，应用也会拦截同主题同范围存在不同规范值的情形。版本日期用于引用展示，不代表覆盖优先级。

答案由实际读取的原文生成，模型不能将自由编造的 answer 字段带入输出。此设计牺牲自然语言摘要与复杂推理能力，换取小型制度库中直接可核查的依据。`answered` 表示有相关原文，当前尚未实现细粒度的“原文是否回答了所有子问题”的语义判定。

## 两条路径及异常路径

- 明确问题：search → read(P01) → finish(answered)。
- 冲突问题：search → read(D01) → read(D02) → finish(conflict)。
- 空结果：search → 改写查询再次 search → finish(out_of_scope)。
- 读取暂时失败：search → read 失败 → 再 read 成功 → finish(answered)。

上述路径均提供 OfflineMock 记录；本地真实 Qwen3-1.7B 也实际执行了明确答案、冲突、资料外、改写、追问和工具失败路径，见 examples/live。真实读取暂时失败后，模型选择重新检索再读取，形成了与正常路径不同的动作序列。

## 技术选择

Python 标准库让评审无需联网安装依赖即可运行全部离线用例。原生循环方便直接检查模型输入、工具观察和边界处理，因此未引入 Agent 框架。HTTP 模型协议通过单个适配器隔离；接其他服务时需核对 JSON 模式支持。

有限合成库按主题完整召回，避免 top-k 截断隐藏冲突。`topic/scope/value` 是人工维护的结构化元数据，冲突判断依赖其准确性；真实资料接入需要文档清洗、索引和元数据审核。当前固定同义词可覆盖演示改写，不具备通用语义召回能力。

外部请求使用 HTTPS，默认 30 秒超时；本地推理仅允许显式回环地址 HTTP，默认 120 秒超时。自动重定向被禁用。日志不保存凭据或原始服务异常。Trace 包含用户问题和读取资料，本次全部使用合成输入。本项目没有读任意本地文件、执行 shell 或修改外部系统的模型工具。

本地模型请求使用 JSON Schema 约束三个动作的字段，并关闭思考模式。格式约束不替模型选择动作。空问题在输入校验层立即返回 needs_input，避免让模型推测缺失问题。结果保存系统提示 SHA-256，便于核对提示版本。
